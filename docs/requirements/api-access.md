# API route access

Built on branch `landingPage`; the API key and permission labels on branch `apiKey`; sign-in and permission checks (API-18 to API-21) on branch `authSetup`. This is a platform rule with no legacy twin (D-27). The 0.2.0 release rule is "every route declares its access; undeclared routes deny".

## Rules

| ID     | Requirement                                                                                                                                                                                                                                                         | Differs from legacy | Tests                                                                        |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------- | ---------------------------------------------------------------------------- |
| API-15 | New. `createApp` mounts every router through `mountRoutes`, as `{ path, access, router }`. `access` is `public`, `{ permission }`, or `{ permission, apiKey: true }` (API-16). A group with no access label, or an unknown one, stops startup. A path that is not mounted answers 404. | New (D-27)          | `api/src/shared/mountRoutes.test.ts`, `api/src/app.test.ts` ("route access") |
| API-16 | New. An access label is `public`, `{ permission }` (a signed-in user whose roles hold it, API-19), or `{ permission, apiKey: true }` (the same, and a valid API key gets in with no permission check) (D-96). Checked in this order: a user whose roles hold the permission gets in (a wrong `x-api-key` sent beside the sign-in is ignored, as on a public route); the API key gets in where the group accepts it; if the session lookup failed and nothing else lets the caller in, 503 `{ message: "Sign-in could not be checked. Try again." }`; no valid key and no user, 401 `{ message: "Missing or invalid credentials." }`; anyone else (a user without the permission, or the API key on a group that does not accept it), 403 `{ message: "You do not have permission to do this." }`. Every path under the group is checked. The key comes from `API_KEY` (required, 32 characters or more) in the `x-api-key` header; a wrong key on a public route is ignored (D-95). The API key holds no permissions. | New. Legacy has one key and no permissions (`SEC-02`) | `api/src/shared/mountRoutes.test.ts`, `api/src/config.test.ts` |
| API-17 | New. `GET /v1/me` is public and tells a caller who it is and what it may do. 200 `{ apiKey, user }`: `apiKey` is true for a valid key; `user` is `{ id, email, name, roles, permissions }` for a signed-in user, or `null`. `permissions` is every permission the roles hold, so the web app keeps no list of its own (D-96, D-102). A user with no role is signed in with empty lists. A wrong key is 401 `{ message: "Invalid API key." }`, even beside a good sign-in. If the session lookup failed, 503 `{ message: "Sign-in could not be checked. Try again." }` and not `user: null`, so an outage is not mistaken for being signed out. One request can carry both a key and a sign-in. Every answer, errors included, is `Cache-Control: no-store`. The request line names the caller type and the user id, never the key or the email. | New (D-95, D-96, D-102) | `api/src/features/me/routes.test.ts`, `api/src/shared/auth/createAuth.db.test.ts` |
| API-18 | New. Sign-in is Better Auth inside the API (D-98), at `/v1/auth`, and only two of its paths are open (the rest answer 404; see [better-auth-routes.md](../better-auth-routes.md)). `POST /v1/auth/sign-in/email` takes `{ email, password }` and answers 200 `{ redirect, user }` with a session cookie (the web app ignores the body and asks `GET /v1/me`; a hook removes `token`, the session token without its signature, from the answer): `HttpOnly`, `SameSite=Lax`, `Secure` when `AUTH_BASE_URL` is https, 12 hours (D-99). A wrong password and an unknown email both answer 401 with the same body and no cookie. A banned user is refused (403). `POST /v1/auth/sign-out` ends the session and clears the cookie. If the database cannot be reached, sign-in answers 503 `{ message: "Database unavailable" }` like every other route (D-32), and any other unexpected failure is a generic 500 `{ message: "Internal server error" }`, both logged with the request id and never printed to the console. Sign-out is the exception: Better Auth clears the cookie and reports success even when it cannot delete the session (it lives at most 12 hours more). There is no public sign-up. The session is kept in the database, so it ends the moment it is deleted or the user is banned. A session used after an hour renews to 12 hours from then, and the new cookie goes back with that response. Settings: `AUTH_SECRET` (32+ characters) and `AUTH_BASE_URL` (scheme and host, no path); both required. | New (D-98, D-99, D-100) | `api/src/features/auth/routes.test.ts`, `api/src/shared/auth/createAuth.test.ts`, `api/src/shared/auth/createAuth.db.test.ts`, `api/src/config.test.ts` |
| API-18a | New. Sign-in is protected two ways beyond the password. **Throttle:** 10 refused sign-ins (4xx) per client address per 15 minutes, then 429 `{ message: "Too many sign-in attempts. Try again later." }` with `Retry-After`; a success does not count, and neither does a failure of ours (a 5xx never uses up anyone's attempts). **Origin:** a sign-in, or any request that carries the cookie, from a page not in `CORS_ORIGIN` is a 403, in every environment (a missing `Origin` header with the cookie too). The log line for a request never shows a one-time token in the path (a reset link, `redactSecrets`). Failed sign-ins are logged without the email or password and counted in `tournament_director.auth.failures` as `bad_sign_in` and `sign_in_throttled`. | New | `api/src/features/auth/routes.test.ts` |
| API-19 | New. Roles map to permissions in one table in `api/src/shared/auth/roles.ts` (D-96, D-97). **Score keeper:** `scores.write`, `registrations.read`, `lanes.read`. **Director:** every permission except `users.manage` and `bowlers.ssn`. **Admin:** every permission, by rule, so a new one reaches the admin at once. A user holds one or more roles, stored as `director,scoreKeeper`, and holds the union of what they grant (D-103). A name that is not a role (a typo, other capitals, `none`) grants nothing. A role change applies on the user's next request. | New (D-96, D-97, D-103) | `api/src/shared/auth/roles.test.ts`, `api/src/shared/auth/caller.test.ts` |
| API-20 | New. Who is calling is worked out once per request, before any route (`identifyCaller`): the API key, the session cookie, both, or neither. A request with no session cookie costs no database read. A user with `banned` set counts as signed out on the next request, even if only the column changed. If the session lookup fails, the caller is not called signed out: protected routes answer 503 (API-16) and `GET /v1/me` answers 503 (API-17); public routes work as usual. | New (D-95, D-96) | `api/src/shared/auth/caller.test.ts`, `api/src/shared/mountRoutes.test.ts` |
| API-21 | New. The first admin comes from `npm run users:create-admin`: a real terminal only, email, name, and a password typed twice and never shown (12 to 128 characters). It needs only `DATABASE_URL`, names the database before it asks anything, and asks before adding to a database that has users. `npm run db:seed` adds one user per role (`admin@example.com`, `director@example.com`, `scorekeeper@example.com`) to a local database only, and refuses when the table holds anyone else or the database holds a tournament that is not a sample (a tunnel to production looks local); `--force-users` overrides that. The sign-in tables come from `api/prisma/auth-tables.sql` (D-100). | New (D-101, D-104) | `api/src/db/createAdminUser.test.ts`, `api/src/db/createAdminUser.db.test.ts`, `api/src/db/terminalPrompts.test.ts`, `api/src/db/seedUsers.db.test.ts`, `api/src/db/localDatabase.test.ts` |

## Notes

- Mounted today, all `public`: `/health`, `/ready`, `/v1/me`, `/v1/auth` (sign-in and sign-out only), `/v1/tournaments`, and the web-only routes under `/v1/tournaments/:id/` for divisions, squads, sweepers, registrations, the lane pages (`squads/:sessionId/lanes` and `sweepers/:sessionId/lanes`), and the recap sheets (`squads/:sessionId/recap-sheets` and `sweepers/:sessionId/recap-sheets`), the scores (`squads/:sessionId/scores` and `sweepers/:sessionId/scores`), and the results (`squads/:sessionId/results` and `sweepers/:sessionId/results`).
- `/v1/tournaments/:id/registrations` shows bowler names and entries. It ships public only because 0.2.0 has no auth. The lock-down release right after 0.3.0 puts it, and any other public read route that should not be public, behind auth (D-46, D-52).
- The recap sheets show bowler names and handicaps, so they ship public for the same reason, and the lock-down release puts them behind auth (D-66, D-52).
- The lane pages show bowler names and averages, so they ship public only for the same reason, and the lock-down release puts them behind auth too (D-59, D-52).
- The scores are public for good, so viewers who are not signed in watch scores come in. The lock-down release leaves them alone; only entry will need sign-in (D-70).
- The results are public for good, like the scores: viewers who are not signed in watch standings. The lock-down release leaves them alone (D-74). The at-large, seeding, and super sweeper routes (`/v1/tournaments/:id/at-large`, `/seeding`, `/super-sweeper`) are public for good too (D-85).
- The API enforces access; the web app only hides what a user cannot use (D-19).
- Do not call `app.use` with a router in `app.ts`. See `docs/api-standards.md`.
- No mounted route needs a permission yet. The lock-down release (D-52) labels the registrations, lanes, and recap sheet routes, and the first command features add the rest. The permission check is tested with test route groups in `mountRoutes.test.ts`.
- Stage 3 (user screens, invites, forgot password) is not built: see D-101, D-103, and Q-34.
